# LY挂机控制台连续对话交接复盘文档

## 一、本次对话沟通经验总结

### 1. 需求演进总览

1. 项目最初目标是制作一个可以在 Minecraft Java 服务器内长期在线的云端挂机控制项目，用户希望它可以部署到自己的轻量云服务器，并支持批量登录多个账号。

2. 用户明确要求脚本、配置说明、示例、注释尽量使用中文。尤其是所有需要填写参数的位置，都要写清楚用途、填写格式和示例。

3. 用户不希望界面提示强调“挂机机器人”，更希望使用“LY挂机控制台”“云端挂机平台”“网页控制面板”等表述。

4. 用户提供参考站点 `http://103.236.99.176:20123`，并粘贴“落渝挂机”的功能介绍，要求最终效果在功能结构和易用性上超过参考站。

5. 前期实现偏 UI，用户反馈“软件的功能还没有写出来，只看到了 UI”。后续开发重点因此转向真实可运行的 Mineflayer 执行端、控制台后端、配置保存、运行日志、命令发送、账号管理和部署脚本。

6. 用户要求把原本顶部的功能选择移动到左侧，并做成可收放侧边栏。后续又要求把“便捷管理、架构优势、安全可靠、适用人群”等介绍集合到“平台概览”里。

7. 用户要求侧边栏标题从“落渝挂机控制台”改为“LY挂机控制台”，并新增“设置”功能，用于控制界面名称、位置、注释等 UI 文案。

8. 用户提供了本地下载的 MCC / MinecraftClient 文件作为参考，包括 `MinecraftClient.backup.ini`、`MinecraftClient.ini`、`MinecraftClient-20240114-240-win-x64.exe`，希望参考已有项目的配置方式。

9. 用户计划部署到 Ubuntu 24.04 轻量云服务器，曾提供公网 IP `116.62.191.104` 和私有 IP `172.25.45.1`。后续明确要求这两个地址不能写死为默认值，而是脚本运行时自动检测“当前公网 IP”和“当前私有 IP”。

10. 用户要求提供一键启动、一键部署、一键更新脚本，并希望命令行菜单有状态提示和进度条，避免不知道脚本正在下载、安装还是报错。

11. 用户要求推送到 GitHub 仓库 `https://github.com/bykedie/LY-.git`，项目命名为“LY控制台”，并在仓库内写简介、功能介绍、部署教程和项目结构说明。

12. 用户在服务器实际执行一键部署命令时，多次遇到 GitHub 访问超时、脚本无进度、安装目录已存在、依赖缺失、菜单退出被判断为失败等问题，因此部署脚本经历了多轮修复。

13. 用户在功能使用中持续提供真实日志，例如 Minecraft 版本不匹配被踢、AuthMe 注册提示、自动登录重复发送、运行控制命令无法使用、日志无法拖选复制等。这些日志是后续修复的主要依据。

14. 后期需求集中在更细的交互体验和数据保留：功能项改为可展开参数面板、账号池、配置档案、启动前选择账号、更新不重置账号和服务器配置、重置默认需要二次确认并等待 5 秒。

15. 当前文档的目标是把全程上下文整理成可交接的 Markdown 复盘，方便下一轮对话或下一个接手者无缝继续开发。

### 2. 主要需求偏差和理解分歧

1. “做一个项目”最初容易被理解为先做界面原型，但用户实际需要的是能真实连接 Minecraft 服务器、批量账号运行、网页控制和远程部署的完整系统。

2. 用户说“功能需要爬下来”时，实际意思是参考并实现参考站展示的功能分类和能力，不是只复制文案，也不是单纯爬网页保存内容。

3. 用户要求“批量登录账号”不仅是账号表单，还包括多账号启动、每个账号独立连接、自动重连、注册密码预留、账号池、备注、启动前选择部分账号运行。

4. 用户对“自动注册”的服务器流程有非常具体的真实行为，前期通用逻辑没有完全匹配 AuthMe 提示，导致多轮调整。

5. 用户对“自动登录”的预期是只在真正需要登录时发送 `/login 密码`。如果服务器已经提示“已成功登录”或“欢迎回来，已帮你自动登录到此服务器”，就不能再重复发送登录指令。

6. 用户反馈“第二次注册命令通过网页发送可以成功”，说明 Mineflayer 聊天发送通路可用，但自动检测或功能启用条件可能不满足。后续确认“智能交互 > 自动登录”必须启用，否则内置注册逻辑不会执行。

7. 用户对运行控制里的手动发送预期是只要挂机进程正在运行就能发送，不应被“发送游戏信息 / 指令”功能开关阻断。后续已改为运行中即可发送。

8. 用户不清楚“监听地址”“开放端口访问”“域名访问”的区别，因此部署脚本和文档需要用普通语言解释：监听地址是程序绑定在哪个网卡，开放端口是通过 `IP:端口` 访问，域名访问是通过 Nginx 和域名解析访问。

9. 用户一键部署时最关注“现在卡在哪里”，所以脚本必须输出阶段、当前动作、失败命令、日志文件位置和常见原因，不能长时间无提示。

10. 用户多次反馈版本号未升级，说明服务器可能还在使用旧脚本、GitHub raw 访问缓存或网络失败、`13. 更新项目并重启` 没有完整拉到最新代码。脚本版本、期望版本和更新路径必须清楚显示。

11. 用户要求“一键配置命令行太长，做成缩短版本”，因此脚本页面顶部只应保留一个最常用快捷启动提示，不要堆多个长命令。

12. 用户要求“重新读取和保存配置不要重置账号、服务器配置和自动化方案”，这说明更新脚本必须把运行数据当作用户资产保护，不能覆盖 `.env`、`bot.config.json`、`accounts.json`、`bot.config.profiles/` 和 `bot.config.automations.json`。

13. 用户要求“重置默认”有确认流程，而且确认按钮必须等待 5 秒才能点击，避免误操作导致配置丢失。

14. 用户曾提供的公网 IP 和私有 IP 只是服务器信息，不应该写死进项目默认配置。正确做法是在脚本运行时检测当前服务器 IP，并显示为“当前公网 IP”“当前私有 IP”。

15. 用户多次要求“推送”，说明本项目协作习惯是开发完成后提交并推送到 GitHub，方便服务器通过更新脚本获取最新版本。

### 3. 反复修改的卡点

1. 前端布局卡点：顶部功能选择需要迁移到左侧侧边栏，并且侧边栏要支持收放；后续每个功能项也要变成可展开的倒三角参数面板。

2. 功能完整度卡点：用户不满足只看到 UI，需要真实运行端、日志、命令发送、配置保存、账号管理和 Mineflayer 连接。

3. 配置说明卡点：用户不清楚服务器配置、域名配置、监听地址、端口开放、账号参数怎么填，因此要求每个填写点都带中文解释和示例。

4. 部署体验卡点：服务器访问 GitHub 慢或超时，导致 `git ls-remote`、GitHub raw、GitHub tar.gz 下载失败或卡住。

5. 部署残留卡点：上一次失败留下 `/opt/ly-console` 目录，后续脚本不敢覆盖，出现“安装目录已存在，无法覆盖”。

6. 菜单脚本卡点：`./deploy/ly-afk-manager.sh < /dev/tty` 退出码被 bootstrap 当成失败，导致用户看到第 146 行失败，但实际可能只是菜单退出或输入流处理问题。

7. 依赖缺失卡点：运行挂机进程时报错 `Cannot find package 'dotenv' imported from /opt/ly-console/src/index.js`，说明服务器项目代码更新后没有安装 npm 依赖。后续增加了依赖检测和自动安装。

8. jsDelivr 备用下载卡点：出现 `RuntimeError: jsDelivr 没有返回项目文件列表`，原因是解析 jsDelivr flat API 时没有兼容返回结构，后续改为更稳的文件列表解析逻辑。

9. Minecraft 协议版本卡点：用户日志出现 `Outdated server! I'm still on 1.12.2`，原因是目标服务器版本和客户端协议不匹配，需要在配置中选择或安装匹配的 Minecraft 协议版本。

10. 自动注册逻辑卡点：用户服务器第一次注册提示内容是 `请输入“/register <密码> <再输入一次以确定密码>”以注册`，实际有效命令是 `/register 密码 密码`。固定 5 秒延迟方案没有稳定复现，最终回到检测提示文本后发送确认注册命令。

11. 自动登录误触发卡点：服务器提示 `欢迎回来，已帮你自动登录到此服务器` 和 `已成功登录！` 后，旧逻辑仍因为消息里含“登录”而发送 `/login 密码`，导致“你已经登陆过了”。后续改为只检测真正的登录提示，不把成功提示当成登录提示。

12. 手动命令发送卡点：运行控制里的账号选择和输入框一度无法发送或受功能开关影响。用户通过网页手动发送 `/register 密码 密码` 成功后，确认手动发送通路必须稳定可用。

13. 日志复制卡点：日志区域拖动时会从左上角第一个字开始选中，影响单行复制。后续改为更适合拖选复制的日志交互。

14. 账号池流转卡点：用户希望账号池中的账号加入账号列表后，从账号池消失，并保留备注；账号列表不再显示“同步配置”，该能力移动到账号池。

15. 启动账号选择卡点：用户希望启动挂机之前选择本次启动哪些账号，而不是启动后才选择目标账号。后续在运行控制中加入“本次启动账号”复选列表，默认选中所有启用账号。

### 4. 高效沟通方式总结

1. 用户提供真实运行日志最有效。日志中的时间、账号名、游戏消息和系统报错可以直接定位部署问题、依赖问题、协议问题、自动登录误判或 UI 交互问题。

2. 用户用具体页面位置描述需求最有效，例如“侧边栏”“运行控制下方日志”“智能交互里的自动登录”“服务器配置里的每个位置”。

3. 对服务器部署问题，用户应尽量同时提供执行命令、终端输出、失败行号和 `/tmp/ly-console-bootstrap.log` 关键片段。

4. 对 Minecraft 游戏内逻辑，用户应直接贴游戏消息原文，因为不同 AuthMe 或登录插件的提示文字差异很大。

5. 对 UI 调整，用户可以描述“现在是什么样、希望变成什么样、点哪里出现什么”。

6. 对自动注册和自动登录，后续必须先确认两个条件：账号是否填写“注册密码预留”，智能交互里的“自动登录”是否启用。

7. 对版本更新，用户如果说“更新后还是旧版本”，应同时确认控制台菜单顶部版本、bootstrap 输出版本、GitHub 最新提交和服务器 `/opt/ly-console` 目录当前代码是否一致。

8. 对部署访问，后续需要先分清两类地址：Minecraft 服务器地址是游戏连接目标；LY 控制台访问地址是浏览器访问面板地址。

### 5. 后续沟通规范和避坑建议

1. 新需求最好按“页面位置、当前表现、目标表现、是否需要保存数据、是否需要同步到服务器脚本”五项说明。

2. 涉及命令行脚本时，需要说明是在本地 Windows 运行，还是在 Ubuntu 服务器运行。

3. 涉及账号、密码、服务器地址时，文档和示例可以写格式，但真实密码不要提交到 GitHub 仓库。

4. 任何更新脚本都必须默认保护用户数据文件，不允许覆盖 `.env`、`bot.config.json`、`accounts.json`、`bot.config.profiles/`、`bot.config.automations.json`。

5. 修改自动登录或自动注册时，必须配套更新 `scripts/auto-login-integration-test.js` 和相关 Dashboard 协议测试。

6. 修改部署脚本时，需要同步改 `deploy/bootstrap.sh` 和 `deploy/ly-afk-manager.sh` 的版本号，并保证菜单显示版本、bootstrap 期望版本一致。

7. 修改 UI 功能时，需要检查移动端、侧边栏收放、表单宽度、日志选择、按钮禁用状态。

8. 修改运行控制手动发送功能时，要确认它不依赖“发送游戏信息 / 指令”开关，只依赖挂机进程是否正在运行。

9. 遇到 GitHub 国内访问慢时，优先通过脚本的 Git clone、GitHub tar.gz、jsDelivr fallback 逐级尝试；如果都失败，说明服务器网络需要代理、镜像源或手动上传包。

10. 如果用户说“一键命令不动了”，下一步应先让脚本输出阶段进度和当前下载源，而不是马上让用户重装。

11. 如果日志显示 `Outdated server! I'm still on 1.12.2`，优先排查 Minecraft 协议版本。

12. 如果日志显示 `Cannot find package 'dotenv'`，优先排查 `node_modules` 是否存在、`npm install --omit=dev` 是否执行成功、服务器是否能访问 npm 源。

13. 如果用户已经用网页发送命令可以成功，而自动逻辑没有发，优先检查功能开关、检测文本是否匹配、日志中是否有“自动登录发送：...”记录。

14. 后续接手者要把“用户最终真实使用体验”放在优先级最高的位置：用户不熟悉命令行和服务器概念，所以所有脚本输出、文档和表单注释都要直白。

## 二、项目整体构造基础信息

### 1. 项目定位和交付目标

1. 项目名称：LY挂机控制台，也可简称 LY控制台。

2. 项目仓库：`https://github.com/bykedie/LY-.git`。

3. 项目目标：提供一个可部署到轻量云服务器的 Minecraft Java 云端挂机控制面板，让用户通过浏览器管理多个游戏账号的连接、自动注册登录、挂机功能、运行日志和命令发送。

4. 服务对象：Minecraft Java 玩家、需要批量管理账号的用户、希望用浏览器远程操作服务器内账号的用户、需要长期在线挂机和自动化辅助的服务器使用者。

5. 最终交付形态：Node.js 项目、静态网页控制台、Mineflayer 执行端、Ubuntu 24.04 一键部署脚本、命令行管理菜单、部署教程、项目结构文档和本交接复盘文档。

6. 项目不是 C# 项目。当前 LY 控制台主体使用 Node.js 和浏览器原生 HTML/CSS/JavaScript 实现。用户提供的 MCC / MinecraftClient 参考文件可能来自其他客户端项目，但当前仓库没有采用 C# 技术栈。

### 2. 核心用途

1. 浏览器管理：用户打开网页面板后，可以配置服务器地址、账号列表、账号池、功能开关、定时任务、界面文字和部署访问说明。

2. 批量账号挂机：通过 Mineflayer 启动多个 Minecraft Java 账号，按账号分别连接目标服务器。

3. 自动注册和自动登录：针对常见 AuthMe 登录插件提示，自动发送 `/register` 或 `/login` 命令。

4. 运行控制：用户可以启动挂机、停止挂机、查看实时日志、选择账号发送聊天内容或 `/` 指令。

5. 功能配置：支持战斗挂机、自动钓鱼、自动进食、自动重生、移动辅助、防挂机走动、快捷栏切换、关键词回复、预设消息、进服发言、远程命令、大厅使用物品和定时任务。

6. 配置档案：用户可以保存多套服务器配置，并用自定义昵称区分不同服务器，避免每次更新或切换服务器都重新填写。

7. 部署管理：Ubuntu 菜单脚本支持安装、启动、停止、重启、更新、查看日志、配置端口、配置域名、安装 HTTPS、开放防火墙端口等操作。

### 3. 技术栈

1. 后端运行语言：Node.js，项目使用 ES Module，即 `package.json` 中的 `"type": "module"`。

2. Minecraft 执行库：`mineflayer`。

3. 寻路能力：`mineflayer-pathfinder`。

4. 环境变量：`dotenv`。

5. Minecraft 数据结构依赖：`prismarine-chunk`、`prismarine-item`、`vec3`。

6. 前端：原生 HTML、CSS、JavaScript，没有 Vue、React、Vite 或 Webpack 构建步骤。

7. 部署守护：推荐使用 `pm2` 管理面板进程。

8. 反向代理：推荐使用 Nginx 配置域名访问。

9. HTTPS：推荐使用 Certbot 申请 Let’s Encrypt 证书。

10. 防火墙：Ubuntu 服务器使用 `ufw` 开放端口。

11. 测试：使用 Node.js 脚本进行语法检查和集成测试，测试脚本位于 `scripts/`。

12. 本地开发环境：Windows PowerShell。注意本地没有 Bash 环境时无法直接执行 `bash -n` 检查 shell 脚本。

13. 服务器目标环境：Ubuntu 24.04，root 权限或可 sudo 的账号。

### 4. 目录和模块划分

1. `src/index.js`：Minecraft 执行端主程序。负责读取配置、校验账号、启动 Mineflayer 客户端、处理自动注册登录、自动重连、战斗、钓鱼、自动吃饭、防挂机移动、定时任务、关键词回复和 stdin 命令。

2. `src/dashboard.js`：网页控制台后端。负责提供 HTTP 服务、静态资源、配置 API、账号池 API、配置档案 API、启动和停止挂机进程、运行日志缓存、Basic Auth、运行中手动发送聊天或指令。

3. `public/index.html`：控制台页面结构。包含侧边栏、平台概览、服务器配置、账号列表、账号池、功能区、定时任务、运行控制、设置等页面元素。

4. `public/app.js`：控制台前端逻辑。负责读取和保存表单、渲染账号池和账号列表、配置档案、启动前账号选择、功能项展开收起、日志交互、请求后端 API、显示提示。

5. `public/styles.css`：控制台样式。负责侧边栏、响应式布局、卡片、表单、功能展开面板、日志区域、按钮状态等视觉表现。

6. `public/log-renderer.js`：Minecraft 日志颜色渲染。负责把 MC 颜色代码或日志文本渲染成更接近游戏控制台的效果。

7. `deploy/bootstrap.sh`：一键拉取部署入口脚本。用于服务器第一次安装或重新拉取项目，处理 GitHub、压缩包和 CDN 备用下载。

### 2. 控制台整体执行流程

1. 用户通过浏览器打开 LY 控制台。

2. `src/dashboard.js` 返回 `public/index.html`、`public/app.js`、`public/styles.css` 和其他静态资源。

3. 前端调用 `/api/config` 读取当前配置。

4. 用户在页面修改服务器、账号、功能开关、账号池、配置档案、UI 设置等。

5. 前端把配置提交给后端，后端校验并写入 `bot.config.json` 或配置档案目录。

6. 用户在“运行控制”里选择本次启动账号。

7. 用户点击启动挂机。

8. 前端向后端发送启动请求，并带上本次选择账号列表。

9. `src/dashboard.js` 校验配置和账号，检查依赖是否存在，如果缺少依赖则自动执行 `npm install --omit=dev`。

10. 后端复制一份运行时配置，并按本次选择账号过滤账号列表。

11. 后端启动子进程 `node src/index.js`。

12. `src/index.js` 读取配置并启动 Mineflayer 客户端。

13. 每个启用账号按配置连接 Minecraft 目标服务器。

14. 执行端把系统日志、游戏消息、自动发送记录输出到 stdout。

15. Dashboard 后端收集 stdout 和 stderr，放入内存日志数组。

16. 前端定时拉取运行状态和日志，显示在“运行控制”日志区域。

17. 用户可以在运行中选择全部账号或单个运行账号，输入聊天内容或 `/` 指令，通过 Dashboard 写入子进程 stdin。

18. `src/index.js` 解析 stdin 命令后调用对应账号的聊天发送能力。

19. 用户点击停止挂机后，Dashboard 向子进程发送停止信号，执行端停止所有账号并退出。

20. 进程退出后，Dashboard 标记运行状态为停止，日志显示退出码。

### 3. 数据流转链路

1. 输入来源一：用户在网页表单填写服务器地址、端口、账号、密码、功能参数和 UI 设置。

2. 输入来源二：用户在账号池维护已注册账号和备注。

3. 输入来源三：用户在运行控制中选择本次启动账号和手动发送内容。

4. 输入来源四：Minecraft 服务器返回的游戏消息，例如注册提示、登录提示、成功登录提示、被踢原因。

5. 处理阶段一：前端 `public/app.js` 把表单数据整理成配置对象。

6. 处理阶段二：后端 `src/dashboard.js` 校验配置对象，保证端口、账号、注册密码、账号池、功能参数类型正确。

7. 处理阶段三：后端写入配置文件或配置档案，作为长期保存数据。

8. 处理阶段四：启动时后端过滤本次选择账号，生成运行时配置。

9. 处理阶段五：执行端 `src/index.js` 建立 Mineflayer 会话并执行功能逻辑。

10. 输出一：浏览器显示保存成功、启动成功、停止成功、错误提示等 UI 反馈。

11. 输出二：日志区域显示挂机进程日志、游戏消息、自动登录发送、网页发送和错误堆栈。

12. 输出三：Minecraft 服务器收到聊天内容、命令、移动、攻击、钓鱼、进食、切换物品等行为。

13. 输出四：部署脚本在服务器终端输出安装、下载、更新、重启、端口和域名配置状态。

### 4. 自动注册和自动登录最终逻辑

1. 自动注册和自动登录都归在“智能交互 > 自动登录”功能下面。

2. 账号必须填写“注册密码预留”，否则自动注册和自动登录不会执行。

3. 如果“智能交互 > 自动登录”没有启用，即使游戏日志出现注册提示，也不会自动发送 `/register`。

4. 执行端收到游戏消息后，先判断是否是已登录成功类消息。

5. 已登录成功类消息包括：`已成功登录`、`已帮你自动登录`、`已经登陆过了`、`已经登录过了`、`已登录`、`已登陆`。

6. 一旦检测到成功登录类消息，会标记当前账号会话已经登录成功，后续不会再发送 `/login`。

7. 真实登录提示判断要更严格，只在消息包含 `/login`、`login password`、或同时包含“请输入”和“登录”时才发送 `/login 密码`。

8. 不能因为消息里出现“登录”两个字就发送 `/login`，因为 `欢迎回来，已帮你自动登录到此服务器` 是成功提示，不是输入提示。

9. 注册确认提示使用精确片段检测：`请输入“/register <密码> <再输入一次以确定密码>”以注册`。

10. 检测到上述注册确认提示后，执行端发送 `/register <注册密码> <注册密码>`。

11. 例如账号的注册密码预留是 `asd123.`，则发送 `/register asd123. asd123.`。

12. 对更普通的注册提示，如果只检测到 `/register`、`register` 或“注册”，但不是二次确认提示，则发送一次 `/register <注册密码>`。

13. 每个账号会话用状态位避免重复发送同一种命令，包括 `loginCommandSent`、`registerSingleCommandSent`、`registerConfirmCommandSent` 和 `loginSuccessDetected`。

14. 自动发送的内容必须写入运行日志，日志格式类似 `自动登录发送：/register 密码 密码` 或 `自动登录发送：/login 密码`。

15. 用户手动通过网页发送的内容，日志格式类似 `网页发送：/register asd123. asd123.`。

16. 用户曾验证过，网页手动发送 `/register 密码 密码` 可以注册成功。因此如果自动注册不生效，优先排查自动登录开关、注册密码、检测文本和自动发送日志。

17. 用户明确要求恢复检测提示逻辑，不采用固定延迟 5 秒方案，因为固定延迟方案在真实服务器上没有稳定生效。

18. 后续如果要扩展更多服务器登录插件，应新增可配置的提示匹配规则，而不是把所有“登录”“注册”字样都当作命令触发条件。

### 5. 启动前选择账号逻辑

1. 运行控制区增加“本次启动账号”复选列表。

2. 列表来源是账号列表中 `enabled !== false` 且用户名不为空的账号。

3. 默认选中所有启用账号。

4. 用户可以全选或清空，再手动选择本次要启动的账号。

5. 启动时前端把选中的账号名数组传给后端。

6. 后端校验每个账号都必须存在，并且必须是启用状态。

7. 如果用户没有选择任何账号，提示至少选择一个账号。

8. 运行时只过滤本次启动账号，不修改保存配置中的账号启用状态。

9. 这样用户可以临时只启动某几个账号，不影响下次默认配置。

10. 停止后可以重新选择下一次启动账号。

### 6. 账号池和账号列表逻辑

1. 账号池用于存放注册完成或准备复用的账号。

2. 账号池中的账号字段包括用户名、注册密码预留和备注。

3. 注册密码预留不隐藏，用户要求直接可见，方便复制和核对。

4. 账号池账号加入账号列表时，账号池里应移除该账号。

5. 加入账号列表后，备注必须保持加入前的内容。

6. 账号列表中不再显示原来的“同步配置”功能，该功能移动到账号池相关操作里。

7. 账号列表用于当前配置实际启动账号，账号池用于备用账号沉淀。

8. 保存配置时，账号列表和账号池都应写入配置文件或配置档案。

9. 更新代码和重新拉取项目不能清空账号列表和账号池。

10. 如果后续要做“注册机器人”，账号池可以作为注册完成账号的落库位置。

### 7. 功能项展开收起逻辑

1. 用户要求“自动走路”等功能不要只有一个启用开关，而是点击倒三角后展开参数设置。

2. 该交互扩展到其他功能项，包括战斗、钓鱼、自动进食、防挂机走动、切换手持、关键词回复、预设消息、远程命令、自动登录、大厅功能和定时任务。

3. 每个功能项标题区域包含倒三角、功能名称、简短说明和启用开关。

4. 点击倒三角或标题区域展开后，显示该功能可调整参数。

5. 展开状态保存到浏览器 `localStorage`，下次打开保持用户习惯。

6. 没有额外参数的功能也要显示中文说明，不要展开后空白。

7. 关键词回复的关键词输入框和回复内容输入框必须各占一半宽度，避免第一个框太长导致第二个框无法填写。

8. “发送游戏信息 / 指令”的说明保留在智能交互区，但实际发送入口应在运行控制区。

### 8. 运行控制和日志逻辑

1. 运行控制负责启动、停止、选择本次启动账号、选择发送目标账号、输入聊天内容或命令、显示实时日志。

2. 手动发送命令只要求挂机进程正在运行，不要求“发送游戏信息 / 指令”功能开关启用。

3. 发送目标可以是全部账号，也可以是单个运行账号。

4. 输入内容可以是普通聊天，也可以是 `/` 开头的命令。

5. 后端通过子进程 stdin 把命令传给 `src/index.js`。

6. 执行端把命令发送给指定 Mineflayer 账号，并写入日志。

7. 日志要包含挂机进程启动、读取账号数量、已启用功能、账号连接、进入服务器、游戏消息、自动发送、网页发送、被踢出、重连、停止、退出码。

8. 日志区域必须支持用户拖选复制单行或多行日志。

9. 日志颜色渲染由 `public/log-renderer.js` 处理，用于更接近 Minecraft 控制台体验。

10. 如果日志中“已启用功能”没有显示自动登录，说明自动登录功能没有启用，自动注册和登录不会执行。

### 9. 配置档案和数据保留逻辑

1. 用户可以保存当前配置为一个配置档案，并填写配置昵称。

2. 配置档案适合按服务器保存，例如一个档案对应一个 Minecraft 服务器地址和账号组合。

3. 用户可以选择某个配置档案加载，加载后当前页面表单随之变化。

4. 如果挂机正在运行，加载配置后一般应提示“下次启动生效”，不能强行改动已经运行的进程。

5. 删除配置档案时不能删除默认档案。

6. 代码更新和重新下载时，必须保留配置档案目录。

7. “重置默认”只在用户二次确认后执行，且确认按钮需等待 5 秒可点击。

8. 后续如要支持配置导入导出，可以基于配置档案目录继续扩展。

### 10. 部署脚本实现逻辑

1. 用户服务器系统目标是 Ubuntu 24.04。

2. 一键部署入口是 `deploy/bootstrap.sh`。

3. 管理菜单是 `deploy/ly-afk-manager.sh`。

4. 用户希望短命令完成拉取和启动，长命令只在文档中作为备用。

5. Bootstrap 脚本启动后必须显示版本、安装目录、仓库地址、目标分支和日志文件。

6. 脚本检查基础命令和依赖，例如 `curl`、`git`、`tar`、`python3`、`node`、`npm` 等。

7. 下载项目优先尝试 GitHub Git 仓库。

8. Git 访问失败时，改用 GitHub tar.gz 压缩包。

9. GitHub 压缩包失败时，改用 jsDelivr CDN 文件下载。

10. 下载每个阶段都要有中文状态和进度，不应长时间无输出。

11. 安装目录默认是 `/opt/ly-console`。

12. 如果安装目录存在且是本项目，应进入更新逻辑；如果存在但不是本项目，应提示用户确认后处理，不能盲目覆盖。

13. 更新代码时需要保护 `.env`、`bot.config.json`、`accounts.json`、`bot.config.profiles/`、`bot.config.automations.json`。

14. 菜单脚本提供安装依赖、启动面板、停止面板、重启面板、更新项目并重启、查看日志、配置域名、开放端口等能力。

15. `j` 快捷命令安装到 `/usr/local/bin/j`，用户在服务器终端输入 `j` 即可打开管理菜单。

16. 菜单顶部显示当前版本 `LY 挂机控制台一键管理脚本 v1.0.39` 和 `快捷打开面板：j`。

17. 脚本显示“当前公网 IP”和“当前私有 IP”，通过检测当前服务器网络得到，不能使用用户曾提供的 IP 作为硬编码默认值。

18. 一键部署时关于“监听地址”的说明要写清楚：一般填 `0.0.0.0` 表示允许外部访问；本机测试可填 `127.0.0.1`。

19. 直接端口访问和域名访问可以共存。直接端口访问形如 `http://公网IP:端口`，域名访问需要域名解析到服务器公网 IP，并由 Nginx 反代到面板端口。

20. `v1.0.27` 增加菜单 `15. 修复公网 IP + 端口访问`。启动、重启和更新流程会把 `.env` 中的监听地址显式传给 PM2，避免 PM2 缓存旧的 `127.0.0.1`；修复入口还会设置 `DASHBOARD_HOST=0.0.0.0`、放行 Ubuntu 端口并显示实际监听结果。云厂商安全组仍需用户在轻量云控制台手动放行。

21. `v1.0.28` 将附近实体改为编号卡片，并同步到“寻找实体/NPC”下拉框；NPC 交互后打开的协议窗口会显示菜单物品名称、描述、槽位和数量，菜单项可直接填入动作。每个动作步骤新增独立“执行”按钮，可向所选在线账号即时下发，无需先保存整份配置；自动化方案仍按稳定名称独立持久化。

22. `v1.0.29` 移除 NPC 交互窗口的重复卡片区，只保留一套按原槽位顺序排列的非空菜单项；每个菜单项显示名称、数量和 Lore 提示。交互窗口打开或内容变化时，窗口标题与全部非空菜单项会同步写入运行日志。附近实体列表过滤 Armor Stand，空槽位不再显示。

23. `v1.0.30` 将交互窗口恢复为唯一一套 `0-80` 小槽位网格，实体扫描结果不再铺在页面，而是完整写入“寻找实体/NPC”的下拉框。新增“操作点击窗口”和“按下按键”动作；NPC 交互会先朝向目标，再发送左键攻击或右键激活实体协议包。网页即时动作会等待执行端完成回执，随后自动刷新坐标、窗口和实体数据。按方向前进使用独立的小到达半径，修复短距离被误判为已到达的问题。窗口日志只保留实际按钮、槽位、名称和 Lore，不再输出窗口统计摘要。

24. “全部实体”实际指 Minecraft 协议已经发送给当前客户端、并仍在客户端加载范围内的全部实体；服务器未发送的远距离实体、纯服务端虚拟 NPC 或未生成的实体无法被客户端扫描。

25. `v1.0.31` 恢复交互窗口为较易阅读的响应式九列槽位尺寸。寻找实体/NPC 在发送左键或右键协议后会等待新的标准菜单、聊天按钮或模组界面协议，默认等待 4500ms，也可在动作参数中设置为 0-15000ms。这样可以捕获 NPC 点击后延迟打开的“邀请系统”等箱子菜单，并将标题、物品名、Lore 和槽位同步到网页与日志。执行端同时监听自定义载荷；对于 CustomNPCs 1.12.2 的 `CustomNPCs` 通道，可识别 `DIALOG`、实体 ID 和对话 ID，并写入日志及快照。

26. CustomNPCs 全屏对话与原版箱子菜单不同：`DIALOG` 协议本身只发送实体 ID 和对话 ID，按钮文字依赖客户端模组提前同步的对话数据。未完成 Forge/CustomNPCs 客户端数据同步前，控制台只能记录通道和编号，不能把屏幕上的三个按钮错误地假定为普通背包槽位；标准箱子式菜单不受此限制。

27. `v1.0.32` 修复服务器输入 `j` 后提示 `ly-afk-manager.sh: Permission denied`。`/usr/local/bin/j` 改为通过 `bash` 或 `sudo bash` 启动管理脚本，不再依赖目标文件的执行位；首次部署同样通过 `bash` 进入菜单，项目更新完成后仍会主动恢复管理脚本的可执行权限。

28. `v1.0.33` 在协议入口过滤 DragonCore 高频 HUD 噪声，包括 `team_expand_`、`YeeCombatView`、`playertag_`、血条视图和 `执行方法('更新数据')` 等数据。命中的载荷不会进入运行日志、协议快照或 NPC 交互响应判断；包含实际 NPC 对话、按钮和菜单文字的 DragonCore 载荷仍会保留。

30. `v1.0.35` 将步骤间的长条添加按钮改为竖向流程连接线和圆形 `+` 节点。步骤 1、步骤 2 等卡片按单列向下排列，点击两个步骤之间的 `+` 会在该位置后插入默认启用的新步骤并自动重新编号；最后一个步骤下方也保留可追加新步骤的 `+`。

31. `v1.0.36` 将桌面端动作序列改成每排五张步骤卡片，从左向右排列并自动换行；步骤之间使用横向连接线和圆形 `+` 节点，每排第五张卡片使用下方节点衔接下一排。窄屏设备继续使用单列纵向流程，避免参数输入框溢出。

32. `v1.0.37` 清理运行控制日志：DragonCore 原始自定义载荷仍保留在协议快照中供界面识别和自动化判断，但不再逐条写入运行日志；标准窗口只输出有意义的菜单物品，忽略没有自定义名称和提示的玻璃板装饰槽位；窗口打开后等待槽位数据稳定再统一输出，减少同一菜单重复刷屏。

34. 如果使用 HTTPS，需要域名解析生效后再通过 Certbot 申请证书。

34. `v1.0.39` 参考 Awwwards 等前端赛事中的专业工作台作品，重做控制台视觉系统：采用深色命令侧栏、浅色高对比工作区、青蓝主色、珊瑚强调色、成功状态色、细网格背景、分层阴影和克制动效。概览、表单、账号、动作序列、窗口槽位、日志和提示状态统一视觉层级；手机端保持固定左侧图标栏。此次只调整展示层，保留全部表单 ID、配置持久化、协议采集与动作执行逻辑。

### 11. GitHub 推送和服务器更新逻辑

1. 开发完成后，本地提交到 `main` 分支并推送到 `https://github.com/bykedie/LY-.git`。

2. 用户服务器通过一键部署命令或菜单中的 `13. 更新项目并重启` 获取最新代码。

3. 如果用户执行更新后版本未变化，可能原因包括 GitHub 访问失败、raw 缓存、服务器仍运行旧目录、更新脚本提前失败、安装目录不是项目 Git 仓库。

4. Bootstrap 中维护 `EXPECTED_MANAGER_VERSION`，用于提示用户期望拿到的最新菜单版本。

5. 如果 GitHub raw 无法访问，可以下载仓库压缩包或使用 jsDelivr fallback。

6. 如果所有下载源都失败，需要考虑服务器网络限制、国内访问 GitHub 超时、DNS 问题或手动上传代码包。

7. 每次修复部署脚本后，都应同步推送仓库，否则用户服务器的更新命令拿不到新脚本。

### 12. 已遇到的真实报错和处理方案

1. 报错：`Outdated server! I'm still on 1.12.2`。

2. 含义：Minecraft 服务器版本和 Mineflayer 客户端协议版本不匹配。

3. 处理：在配置中选择目标服务器对应的 Minecraft 版本，或调整 Mineflayer version 配置，不是部署脚本问题。

4. 报错：`Cannot find package 'dotenv' imported from /opt/ly-console/src/index.js`。

5. 含义：服务器缺少 npm 依赖。

6. 处理：执行 `npm install --omit=dev`，当前 Dashboard 启动挂机前也会检测依赖并尝试自动安装。

7. 报错：`jsDelivr 没有返回项目文件列表`。

8. 含义：备用 CDN 文件列表解析失败或 CDN 返回结构不符合旧逻辑。

9. 处理：更新 bootstrap 的 jsDelivr flat 文件列表解析逻辑。

10. 报错：`脚本在第 146 行失败，失败命令：./deploy/ly-afk-manager.sh < /dev/tty`。

11. 含义：bootstrap 调用菜单脚本时被当作失败，可能是菜单退出码或输入流问题。

12. 处理：菜单退出不应被误判为部署失败；bootstrap 应区分真实安装失败和用户退出菜单。

13. 报错：`安装目录已存在，无法覆盖：/opt/ly-console`。

14. 含义：上次失败留下目录，脚本无法确认是否安全覆盖。

15. 处理：如果确认是上次失败留下的空目录，可以手动删除；更好的脚本逻辑是识别本项目目录后执行更新。

16. 现象：执行一键命令后长时间无输出。

17. 含义：可能卡在 GitHub 下载、Git 检查、DNS、网络超时或 apt 锁等待。

18. 处理：脚本需要显示当前下载源、超时时间和进度条，并把输出写入 `/tmp/ly-console-bootstrap.log`。

19. 现象：已成功登录后仍发送 `/login 密码`。

20. 含义：旧自动登录逻辑把成功提示中的“登录”误判为登录输入提示。

21. 处理：已在 `v1.0.20` 收紧登录提示判断，并把成功登录消息作为抑制条件。

### 13. 测试和验证方式

1. 语法检查命令：`npm.cmd run check`。在 Windows PowerShell 中推荐使用 `npm.cmd`，避免 npm shim 执行策略问题。

2. 完整测试命令：`npm.cmd test`。

3. 自动登录测试：`node scripts/auto-login-integration-test.js`。

4. Dashboard 协议测试：`node scripts/dashboard-protocol-test.js`。

5. 基础冒烟测试：`node scripts/smoke-test.js`。

6. 日志渲染测试：`node scripts/log-renderer-test.js`。

7. 账号校验测试：`node scripts/account-validation-test.js`。

8. 防挂机移动测试：`node scripts/anti-afk-movement-test.js`。

9. 钓鱼、重生、协议等功能也有对应测试脚本。

10. 本地 Windows 无 Bash 时，shell 脚本不能直接 `bash -n`，需要在 Ubuntu 服务器或带 Bash 的环境中验证。

11. UI 修改后，应打开本地面板检查侧边栏、功能展开、账号池、配置档案、运行控制和日志选择。

### 4. 后续排查问题的建议顺序

1. 先确认用户说的问题发生在网页、服务器脚本、Minecraft 连接、自动登录还是 GitHub 更新。

2. 如果是网页问题，先看浏览器当前页面、控制台面板版本、相关 UI 位置和用户操作步骤。

3. 如果是运行问题，先看运行控制日志，并确认“已启用功能”列表。

4. 如果是自动注册或登录问题，先确认自动登录开关、账号注册密码、游戏消息原文和是否出现自动发送日志。

5. 如果是无法连接或被踢，先看踢出原因，重点区分协议版本、账号验证、服务器白名单、登录插件和网络问题。

6. 如果是部署问题，先看 `/tmp/ly-console-bootstrap.log` 和菜单脚本输出。

7. 如果是更新后版本没变，先看菜单顶部版本、GitHub 最新提交、服务器目录是否是 Git 仓库、更新命令是否实际完成。

8. 如果是配置丢失，先停止继续更新，检查 `/opt/ly-console` 下是否有备份文件、配置档案目录和旧目录。

9. 如果是依赖问题，先执行或触发 `npm install --omit=dev`，再重启面板。

10. 如果是端口或域名访问问题，先确认面板本地端口监听，再确认云服务器安全组、ufw、Nginx、域名解析和 HTTPS 证书。

### 5. 当前状态简明结论

1. 当前项目主体是 Node.js + Mineflayer + 原生网页控制台，不是 C#。

2. 当前仓库已具备真实挂机执行端、网页控制台、配置保存、账号池、配置档案、运行日志、手动命令发送、启动前账号选择、自动注册登录和 Ubuntu 部署脚本。

3. 当前自动注册逻辑以检测 `请输入“/register <密码> <再输入一次以确定密码>”以注册` 为核心，检测到后发送 `/register 密码 密码`。

4. 当前自动登录逻辑已避免把 `已成功登录`、`已帮你自动登录` 等成功提示误判为登录输入提示。

5. 当前更新和部署仍可能受 GitHub 国内网络影响，后续最值得继续增强的是下载源容错、网页内更新诊断和注册流程可配置化。

6. 后续接手者可以直接基于本文档、`docs/project-architecture.md` 和 `docs/ubuntu-24.04-deploy.md` 继续沟通和开发，不需要重新梳理上下文。
